## 1. 填写原则

测试时先登记版本和环境，再按用例记录实际观察。执行日志和缺陷报告承担不同作用，结构参考 [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) 的测试产物、追踪和缺陷管理章节，以下字段为本项目使用方式。

1. 每个被测构建、设备或关键权限配置建立明确的 RUN 批次；代码修改后以新批次或明确的新构建记录复测。
2. 用 `TC-编号/子场景名` 标明子场景，填写实际输入及观察，不能只填“成功”或附一个无对应环境的终端截图。
3. 实际结果、截图、视频、日志和 BUG 编号相互对应；通知必须保留计划时刻、实际到达时刻、时区及权限条件。
4. 未运行填“未执行”；环境或待审预期使结果无法判断填“阻塞”并说明原因；观察与确认后的预期不符填“失败”。
5. 修复后新增复测记录，不覆盖原失败记录；实现修改、规则修改与测试数据修改分别说明。
6. 使用本组自建示例任务、联系人与图片；不需要为举例记录真实私人材料。

## 4. 证据保存约定

证据按 `docs/test-evidence/<RUN>/` 保存；本轮已有构建日志、JUnit XML、Lint 报告和诊断摘录，见[首轮证据](test-evidence/RUN-20261027-001/README.md)。尚无实机截图或视频。

- 建议文件名：`TC-编号_子场景_序号.png`、`.mp4` 或 `.txt`；记录中使用相对于本文件的路径。
- 规则测试保留测试命令、输出、代码版本与固定时钟参数；UI 和通知测试保留可核对内容及时间的证据。
- 同一证据可支撑多个明确相关的检查点，但记录需说明对应关系，不能用一张首页截图替代全部用例。
- 无法留存某类证据时，记录原因和可复核的替代观察；未提供证据的项目须在报告中说明。

## 6. 汇总规则

一个 TC 的适用子场景全部通过才记为通过；存在失败则记为失败，并列出尚未完成的其他子场景。没有失败但被环境或预期阻断的记为阻塞；其余未完成的记为未执行，注明是否已有部分观察。

同一个版本的结果按上述口径汇总到[测试报告](test-report.md)。不同代码版本和设备分别列明，不能用旧版本的成功覆盖新版本失败；回归运行次数也不能增加计划用例总数。
