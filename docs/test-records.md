## 1. 填写原则

测试时先登记版本和环境，再按用例记录实际观察。执行日志和缺陷报告承担不同作用，结构参考 [ISTQB CTFL v4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf) 的测试产物、追踪和缺陷管理章节，以下字段为本项目使用方式。

1. 每个被测构建、设备或关键权限配置建立明确的 RUN 批次；代码修改后以新批次或明确的新构建记录复测。
2. 用 `TC-编号/子场景名` 标明子场景，填写实际输入及观察，不能只填“成功”或附一个无对应环境的终端截图。
3. 实际结果、截图、视频、日志和 BUG 编号相互对应；通知必须保留计划时刻、实际到达时刻、时区及权限条件。
4. 未运行填“未执行”；环境或待审预期使结果无法判断填“阻塞”并说明原因；观察与确认后的预期不符填“失败”。
5. 修复后新增复测记录，不覆盖原失败记录；实现修改、规则修改与测试数据修改分别说明。
6. 使用本组自建示例任务、联系人与图片；不需要为举例记录真实私人材料。

## 4. 证据保存约定

证据按 `docs/test-evidence/<RUN>/` 保存；构建日志、JUnit XML、Lint 报告和诊断摘录分别见[第一轮证据](test-evidence/RUN-20261027-001/README.md)和[第二轮证据](test-evidence/RUN-20261027-002/README.md)。[第三批证据](test-evidence/RUN-20261027-003/README.md)保存荣耀 X50 安装启动 JSON 与首页原始截图，尚无实机业务操作视频。

- 建议文件名：`TC-编号_子场景_序号.png`、`.mp4` 或 `.txt`；记录中使用相对于本文件的路径。
- 规则测试保留测试命令、输出、代码版本与固定时钟参数；UI 和通知测试保留可核对内容及时间的证据。
- 同一证据可支撑多个明确相关的检查点，但记录需说明对应关系，不能用一张首页截图替代全部用例。
- 无法留存某类证据时，记录原因和可复核的替代观察；未提供证据的项目须在报告中说明。

## 6. 汇总规则

一个 TC 的适用子场景全部通过才记为通过；存在失败则记为失败，并列出尚未完成的其他子场景。没有失败但被环境或预期阻断的记为阻塞；其余未完成的记为未执行，注明是否已有部分观察。

同一个版本的结果按上述口径汇总到[测试报告](test-report.md)。不同代码版本和设备分别列明，不能用旧版本的成功覆盖新版本失败；回归运行次数也不能增加计划用例总数。

### 13.3 点击、角色及恢复

短时 NEAR 点击由用户反馈进入详情，但独立检查时已切走；EDIT 点击随后反馈其他页面或通知消失，两者未登记设备落点通过。用户另反馈从“今日 DDL”进入应用，汇总具体列表落点及清筛选尚未独立核对。

另建 QA-R3-CLICK，截止北京时间 16:32、速通 30 分钟，用于已经临近时的即时危险提醒和长有效期点击。08:09:15 UTC，自动观察器在用户点按后核对到该事项的真实详情并截图；没有用 ADB Intent 或 input 注入替代用户点击。此样本不计入上述四次未来定时差值。

手机截图核对到逾期认真、危险生气、完成快乐反馈以及素材署名弹窗；完成图仅截到快乐卡片的部分区域，不当作全部布局已检查。角色按全体事项计算，不随 QA 搜索过滤；原有逾期事项影响状态，未修改用户事项来凑普通表情。支盟渊明确要求后续改成更可爱的 Q 版，最终名称“蓝色大肥鱼”，见[审核和候选](character-q-candidates.md)；当前安装包尚未替换图片。

全部送达及点击检查结束后才强停取账本；重开时 CLICK 尚未过期，已 SENT 的危险原因未重新出现，属于本次恢复样本。强停本身会移除系统通知，不能将重开后零通知单独当成取消能力证明。

### 13.4 收尾、问题与未测边界
