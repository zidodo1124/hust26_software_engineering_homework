## 2. 背景、用户与项目目标

### 2.1 背景与问题

大学生同时面对课程作业、学生工作、家庭、生活与社交事务，截止时间分散在不同来源中。用户容易遗忘事项，或直到临近截止才意识到完成任务所需的时间已经不足。文字、截图、链接等关联材料也容易与待办本身分离。

### 2.2 目标用户与使用角色

第一版面向使用 Android 手机的大学生。应用内只有本机使用者这一业务角色，不设置登录账户、管理员或协作成员。课程小组成员是项目开发参与者，不是应用内权限角色。

### 2.3 产品目标

1. 把不同来源的 DDL 集中管理，让用户能够快速记录并找到事项。
2. 通过角色、气泡卡片、紧急标识和统计，让用户看清当前要处理的事情。
3. 结合截止时间与用户估计的“速通时间”，提示需要开始行动的事项。
4. 利用每日汇总、危险期和临近截止通知，在用户未主动查看列表时提供提醒。
5. 保存描述和截图等上下文，减少再次查找原始消息的成本。

目标是辅助用户规划与记忆；应用不能保证用户一定按时完成任务。

## 6. 事件信息与业务概念

### 6.1 事件信息

本表描述用户能够理解的信息，不规定数据库表或实现字段类型。

| 信息 | 必填性 | 含义与约束 |
| --- | --- | --- |
| 标题 | 必填 | 识别事项的主要文字；空白输入的校验方式作为建议待确认 |
| 截止时间 | 必填 | 事项的截止时刻；统一以北京时间呈现，精度与全天事件见 Q-03 |
| 重要程度 | 选填 | 表示用户对事项重要性的判断；选项与默认值待 Q-06 确认 |
| 来源 | 选填 | 例如学习、学生工作、家庭、生活、社交；这些是原文例子，不是已锁定枚举 |
| 标签 | 选填 | 给事件添加便于识别的分类信息；维护方式待 Q-06 确认 |
| 详细描述 | 选填 | 容纳较长文字，可包含任务说明、网址等；查看时可复制文字 |
| 截图附件 | 选填 | 保存原始信息图片，并能在详情中再次查看；导入方式与数量待 Q-05 确认 |
| 速通时间 | 选填 | 用户估计的最少完成耗时，并非已经投入的时长、倒计时总长或自动测量结果 |

长度、图片大小、附件数量等限制尚未确认。后续如确需限制，应给出用户能理解的提示，并在需求修订中记录，而非由实现默默决定。

### 6.2 时间与状态

- **今日 DDL**：截止时间落在北京时间当天的事件；是否排除已完成、归档等事件，取决于 Q-01 的状态方案。
- **危险期**：用户设定的最少耗时已经接近可用剩余时间的阶段。当前概念已确认，精确计算公式与边界待 Q-02 确认。
- **过期**：事件已经越过截止时间；在截止时刻本身如何判定，需随 Q-02、Q-03 一起明确。
- **重要程度**：用户对事件价值或优先级的判断；是否参与紧急度计算待 Q-02 确认。
- **已完成、归档、永久删除**：含义和操作尚待 Q-01 确认。不要把“时间已过期”等同于“用户已完成”。

上述概念用于解释业务，尚未规定互斥的存储状态；时间分类与完成、归档等用户操作如何组合，待 Q-01 确认。

时间变化、用户编辑与用户操作可能同时影响卡片、统计和通知；三者应使用同一套已确认规则。第一版不包含自动判断任务是否真正完成的能力。

## 9. 初步技术轮廓

本节仅帮助理解大体实现方向，属于候选职责划分，不是已经确定的技术架构。

| 能力部分 | 大体职责 | 后续需要验证的事项 |
| --- | --- | --- |
| Android 界面 | 首页角色与气泡卡片、事件表单、详情、日历、批量管理与设置 | 交互样式、设备适配、角色表现形式 |
| 本地数据保存 | 保存事件、用户设置与附件关联，供重启后读取 | 存储方案、附件生命周期、失败处理与数据一致性 |
| 时间与状态规则 | 根据北京时间、截止时间和速通时间计算显示状态与统计 | 时间边界、设备时间变化、未填速通时间等规则 |
| 系统通知 | 根据规则安排三类提醒，并处理通知点击进入应用 | 权限、应用关闭与设备重启等运行条件，以及实际提醒可靠性 |
| 角色素材与台词 | 保存角色表情和台词，按事件状态选择合适表现 | 素材来源、风格一致性、台词覆盖与重复控制 |

单机范围目前不需要引入账号系统或云端服务。具体语言、框架、存储库和通知机制等选择，留待下一阶段调研；若调研发现已确认体验受平台限制，应带着证据回到需求层协商调整。

## 10. 待确认事项与审核入口

以下建议集中列出，均不构成用户已确认需求。用户可以逐项接受、修改或删除；答案应回填对应功能和验收场景，并记录真实修订。

| 编号 | 待确认主题 | 当前建议或需要回答的问题 |
| --- | --- | --- |
| Q-01 | 完成、归档、过期与清理 | 是否提供标记完成／恢复未完成？建议完成后停止提醒并进入历史，过期未完成默认灰显保留；一键清理默认归档，永久删除单独确认。是否采用？批量操作和可配置的过期处理具体支持哪些动作？ |
| Q-02 | 紧急度与速通时间 | 建议危险期定义为 `0 < 截止时间 - 当前时间 <= 速通时间`；未填速通时间不计入危险期；普通临近为剩余不超过 24 小时且尚未过期，显示橙色，危险期红色优先；重要程度单独标识。阈值是否可调、速通时间输入单位与无效值处理需明确。 |
| Q-03 | 时间精度与日历 | 建议按北京时间、截止时间精确到分钟，日历可按日期查看事件。是否需要只选日期的全天事件，并默认当天 23:59 截止？截止时刻本身按什么状态处理？ |
| Q-04 | 通知详细行为 | 建议每日 08:00 汇总今天未完成的 DDL，时间可修改；临近截止默认提前 1 小时，可在设置修改；危险期在进入时触发。还需明确无今日事件时是否通知、是否含逾期事件、点击落点、相同触发时刻如何处理，以及关闭应用和重启设备后的预期。 |
| Q-05 | 截图附件与 OCR | 第一版需要相册选择、粘贴还是两者？是否支持多张？标题与时间仍手动输入，还是要求识别图片后由用户确认？附件查看方式与数量限制尚未确定。 |
| Q-06 | 自定义属性 | 是内置字段加可维护的来源与标签，还是允许用户新增任意字段？重要程度选项与默认值是什么？ |
| Q-07 | 列表组织与统计入口 | 建议支持关键词搜索、按来源／标签筛选、按截止时间排序，默认隐藏已完成和归档事件；顶部计数可点击进入对应列表。哪些属于第一版？ |
| Q-08 | 名称、角色与遗漏功能 | 应用名称、角色形象和台词语气是什么？多种表情与丰富台词的验收覆盖如何约定？是否还有必须加入但原文未提到的功能？ |
| Q-09 | 交付环境与课程细节 | 准确验收日期与时刻、具体演示手机及 Android 版本、老师是否另有模板要求尚未确认。已确认先用 Markdown，后续由用户再考虑格式转换。 |
| Q-10 | 质量建议 | 是否采纳第 7 节建议项，包括异常提示、长内容可读性、提醒一致性和通知权限说明？后续确定的数据量、附件上限等限制是否适合实际使用？ |

## 11. 风险与后续衔接

| 风险 | 当前影响 | 处理方向 |
| --- | --- | --- |
| 距离验收约剩 5.5 天 | 大幅扩展功能会压缩实现、联调与演示准备时间 | 先确认核心闭环；新增能力要说明优先级和可接受的取舍 |
| 通知的目标运行条件未定 | 可能出现界面功能完成但手机提醒未达到预期的情况 | 下一阶段优先调研并实机验证三类通知的关键路径 |
| 状态与时间规则不明确 | 首页数量、颜色和通知可能互相矛盾 | 先关闭 Q-01 至 Q-04，再据此设计边界用例 |
| 图片识别或任意字段扩展 | 可能显著增加范围 | 等待 Q-05、Q-06 答复，不能默认实现或默认删除用户需求 |
| 角色素材与台词尚未确定 | 影响整体视觉与体验验收 | 明确来源、风格和覆盖场景；不把素材数量当作已确认指标 |
| 团队贡献与审核记录不足 | 不满足课程对个人多次提交的要求 | 需求确认后安排实际分工，各成员以真实身份提交实际工作；文档审核意见与修订对应保留 |

需求确认后，下一阶段再进行广泛技术调研、可行性验证、详细设计与四人分工。若用户审核改变范围，应先修订需求和对应验收场景，再安排实现。
