## 1. 推进方式

每轮交付可构建的增量，新增功能经过检查后再合入下一轮。先完成“录入—保存—查看—处理”的基本流程，再完善信息组织、图片和系统提醒。完整需求仍保留；分轮只是安排实现顺序，不代表删去未实现功能。

准确验收时间尚未明确，不将早先“约剩 5.5 天”的估计当作实时倒计时。按以下顺序推进，并为荣耀 X50 实机验证、修复和报告整理保留独立时间。

| 轮次 | 目标与范围 | 结束时应有的证据 |
| --- | --- | --- |
| 第一轮：核心流程 | Android 工程；Room 本地保存；标题、截止时间、描述、重要程度和速通时间；创建、编辑、详情、完成／恢复、归档／恢复、确认删除；首页时间分类、今日／危险计数、基础搜索、截止排序；普通紧急阈值设置 | 可重复构建命令、Debug APK、规则及存储自动测试、静态检查；设备未连接时明确保留实机验证项 |
| 第二轮：信息组织 | 来源和标签、自定义文本字段、日期日历、批量管理、过期处理设置；相册和粘贴多图、附件生命周期 | 对应功能及失败路径用例，重开后数据保留，数据库版本变更有迁移检查 |
| 第三轮：提醒与角色 | 每日汇总、危险期和临近提醒；权限、重排、去重与恢复；经核对的单角色表情、预设台词和署名 | 荣耀 X50 的通知时间与权限记录，旧提醒失效检查，素材来源和许可清单 |
| 第四轮：联调与验收 | 跨模块回归、长内容及设备适配、缺陷修复、最终报告和演示 | 与提交号对应的安装包、真实执行记录、遗留问题清单及当前成员可解释的演示流程 |

通知属于设备相关风险较高的功能，岳羽泉在第一轮并行开展权限和调度验证准备，无须等全部页面完成。图片与素材核对也可提前进行，但不影响本轮核心流程交付。

## 3. 本轮采用的暂定规则

本轮按设计中的默认方案实现：恰好截止算过期；标题去除首尾空白后不能为空；速通时间和普通紧急阈值为正分钟数；已完成事项归档及恢复归档时保留完成标记；今日计数包含当天已逾期但未完成、未归档的事项。它们仍可由用户审核调整，实现不等于整体需求已获批准。

界面仅提供本轮已实现的操作，不显示无法使用的通知或图片按钮。尚未接入通知时，不声称应用会在后台发送提醒；角色素材未选定时，不擅自把候选图片加入安装包。

## 4. 质量与合入要求

1. 数据以数据库为依据，完成和归档分别保存；紧急程度从当前时间推导，不能长期缓存为失效状态。
2. 编辑已有事项检查修订号，不覆盖别处已经修改的数据；被删除的事项不能因旧表单保存而复活。
3. 业务时间统一按 `Asia/Shanghai` 输入和展示。测试固定时钟，不靠等待真实小时数验证边界。
4. 每项功能保持清晰的模块职责；数据库升级保留历史数据，禁止用破坏性重建掩盖迁移问题。
5. 先运行必要的单元／存储测试、构建和 Android Lint，再执行可用设备上的流程检查。没有连接实机时只报告已取得的证据。
6. 每次提交对应真实进展或修正；代码提交后，测试记录标明所测提交和构建，不以提交数量替代质量。

## 5. 后续衔接

队友先阅读本人的任务文件，在自己的分支中完成可独立审核的一项工作，再提交或发起 PR。涉及共享模型和数据库字段的改动先写清影响，避免多个人直接修改同一套公共结构。领取、阻塞、完成和验收均由实际参与者更新，功能状态持续记录在[STATUS](../STATUS.md)。
