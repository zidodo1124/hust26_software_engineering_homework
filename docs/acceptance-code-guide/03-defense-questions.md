# 验收提问与答辩练习

适用 `demo-v0.3.5`。**前 5 分钟只操作软件；结束后等老师提问，再按问题作答，不主动接着讲源码。** 临场先用[提问速查入口](README.md)的一句话回答，需要深入时查本页。以下内容供演示前自学和演示后按需回答，建议准备时自己说一遍，再打开代码验证。完整文件地址与固定行号链接集中在[功能源码对照](02-feature-source-map.md)，环境版本集中在[架构与技术栈](01-architecture-and-stack.md)。

## 一、先掌握的总体问题

### 1. 你们做的是什么，解决什么问题？

这是一个面向大学生日常截止事项的本机 Android 应用。它把截止时间、任务说明、来源标签、自定义补充信息和图片集中在一条记录里，并用搜索、日历、状态管理和提醒帮助安排任务。演示时可用“报告、作业、报名”三个样本解释，比罗列所有按钮更直观。

接着指向 D01 的 `MainActivity` 和 `HomeScreen`：前者是 Android 入口，后者展示从业务数据计算出的列表与统计。项目没有账号系统、服务器或云同步，不要用“所有平台共享任务”来介绍。

### 2. 技术栈是什么？Kotlin、Compose、Room、SQLite 分别是什么？

Kotlin 是主要编程语言；Jetpack Compose 是声明式 UI 工具；ViewModel 和 StateFlow 管理可观察状态；Room 提供 SQLite 的实体、DAO、关系查询、迁移和事务抽象；SQLite 才是本地数据库引擎。协程用于异步任务和 IO，AlarmManager／NotificationManager 是 Android 系统能力。

构建环境是 JDK 17、Gradle 8.11.1、AGP 8.9.2，Kotlin 2.1.20；`compileSdk/targetSdk=35`、`minSdk=26`。JUnit、Robolectric 是验证工具，不是手机上展示页面的框架。打开根 `build.gradle.kts` 和 `app/build.gradle.kts` 可以现场核对，而不是背一个与工程无关的版本列表。

### 3. 为什么用原生 Android？架构是不是 MVVM？

这个项目需要直接处理图片授权、应用生命周期、通知权限与系统 Alarm，选择原生 Android 可以直接使用对应接口。代码采用 ViewModel／Repository 分层和状态驱动的 UI，可以说明其 MVVM 思路；但实际只有单个 `:app` 模块，页面由 `SaverApp` 的状态手工切换。

不要说已经引入 Hilt、Navigation、Retrofit、WorkManager 或微服务。现场画出“Compose → ViewModel → Repository → Room；Flow 返回 UI”，再补图片私有文件与提醒平台适配两条支线即可，见[架构图](01-architecture-and-stack.md#2-单-activity分层职责与页面状态)。

### 4. 一次点击“保存事项”到底执行了哪些代码？

按 D02 顺序打开：`EventEditor` 组装 `EventDraft` → `SaverViewModel.save` 经 `perform` 执行 → `EventValidation.normalize` → `RoomEventRepository.save` 写入事项及关联 → 同事务 `ReminderPlanStore.rebuild` → DAO Flow 更新 ViewModel → `SaverApp` 等新 revision 可见后进入详情。图片候选文件回收和提醒校对也由协调层处理。

老师追问“为什么等 Flow？”时说明：Repository 返回保存成功和 Room 观察结果发出更新有先后时序，直接跳到详情可能暂时读不到新记录。`SaverApp.kt` L143—147 检查 ID 与 revision，保证页面已经观察到所需版本。

## 二、演示操作对应的实现问题

### 5. 输入文字时就写数据库了吗？不保存直接返回会怎样？

输入主要更新 `EventEditor` 中的草稿状态，点击保存才提交；dirty 检查决定返回时是否询问放弃。`rememberSaveable` 支持相关页面／Activity 状态恢复，不能等同于草稿永久持久化，也不能保证进程被杀后所有内存任务仍存在。依据：D02，`EventEditor.kt` L78—123。

必填检查在界面用于及时提示，领域层还会重新校验，避免其他调用路径绕过 UI 造成无效数据。当前代码允许保存过去的截止时间并显示逾期，不是“只允许未来日期”；演示选未来时间是为了让结果稳定。

### 6. 单机应用为什么还要 expectedRevision？

即使没有多个网络用户，旧编辑草稿也可能与其他状态变更冲突，例如编辑过程中事项被完成或另一个入口保存。打开草稿时记录 revision，提交时与数据库当前版本比较；不同就拒绝覆盖并保留填写内容。

依据：D02，`RoomEventRepository.kt` L38—41。这是一种乐观并发检查；它不是数据库 schema 版本，也不是 APK 的 versionCode。真正的保存、完成、归档变化会增加事项 revision。

### 7. 一次保存为什么需要事务？数据库和图片文件也是同一个事务吗？

一条事项可能同时有主记录、多个标签关联、字段和附件元数据，业务提交还会影响提醒计划。它们应一起成功或回滚，避免用户看到一半更新。因此 Repository 使用 Room `withTransaction`。

图片字节位于文件系统，SQLite 事务不能自动回滚文件复制。本项目先生成候选副本，保存成功后按数据库引用清理；取消或导入失败则补偿回收未引用候选。必须区分“数据库事务保证”与“跨文件系统的补偿管理”。依据：D02、D03。

### 8. 数据库有几张表？来源、标签和自定义字段有什么区别？

当前 schema 4 注册 9 张表：六张业务表 `events/sources/tags/event_tags/custom_fields/attachments`，再加 `settings/reminder_plans/reminder_control`。报告里的“原六表保持”不是说数据库只有六张表。

来源是单选目录，标签通过中间表实现多对多，自定义字段属于具体事项并保存字段名、内容及顺序。来源存在性／停用关系由 Repository 校验；`events.sourceId` 此版没有声明 Room 外键，不要把所有逻辑关联都称为数据库外键。依据：[数据模型](01-architecture-and-stack.md#3-数据模型与事务为什么演示一次保存会涉及多张表)。

### 9. 为什么关键词有时搜不到？多个词是 AND 搜索吗？

当前是整段连续子串、忽略大小写的搜索，覆盖标题、描述、自定义字段名和内容；去首尾空白，但不把空格分成多个词做 AND。分类名称通过单独筛选，不自动成为关键词字段。先检查原文本里是否有这段连续内容，再检查日期、列表模式和分类条件是否仍生效。

来源、标签、日期等不同条件之间取交集；多个标签使用 `containsAll`，要求全部包含。D04 的 `EventQuery.select` 可以直接展示这两种“相与／相或”的区别。结果按截止时间，再按 ID 稳定排序。

### 10. 为什么搜索结果只有一条，“今日 DDL”却可能大于一？

首页今日统计基于全部未完成且未归档的事项，搜索只缩小当前结果列表。两者回答的问题不同：一个问“今天全局有多少待办”，一个问“当前条件匹配多少”。如果把筛选后的结果当全局统计，用户搜不到时就会被误导为没有今日任务。

依据：D01／D05，`HomeScreen.kt` L54—74。角色反馈同样读取全局事项，因此当前搜索结果为空时角色仍可能显示紧急状态。

### 11. 选中了今天，为什么日历还要显示明天的数量？

日历日期格展示当前列表类型及关键词／分类条件下的日期分布；下方列表展示选中日期的具体事项。代码为两者执行不同范围的查询：`calendarEvents` 没有传当前单日 `date`，再按北京时间日期分组计数。这样选择今天只缩小列表，不把其他日期格错误清零。

依据：D05，`HomeScreen.kt` L63—74。回答时可引用刚才的展示：样本日 S 有 2 条、次日有 1 条，点击样本日 S 后另一日仍有计数。S 不必是今天；“今天”导航不在 5 分钟主线内，老师要求追加且 S 恰为今天时，才用它验证相同范围。

### 12. 周历怎么确定一周？跨年为什么还能工作？

以锚点日期减去 `dayOfWeek.value - 1` 天得到周一，查询范围是周一到下一个周一之前。周期导航使用 `LocalDate.plusDays/minusDays`，周视图步长为 7，日视图为 1；跨月、跨年由日期类型完成运算。

依据：D05 的 `CalendarPeriod` 和 `inWeekView` 条件。日期格前置空位则由 `calendarWeeks` 根据当月 1 日的星期偏移生成，末尾补到 7 的倍数。不要说代码会在跨年时单独把月份手工改成 1。

### 13. 本轮修了什么日历 bug？怎么证明修复有效？

原 `inWeekView` 把 `calendarOpen` 作为条件，导致收起周历面板时查询从整周落回锚点单日。修复移除了面板展开状态的依赖，只按当前视图模式和快捷筛选决定是否为周范围。

新的 `collapsingWeekCalendarPreservesWholeWeekUntilADayIsSelected` 页面测试先在旧条件下失败，再在修复后通过；完整本机 224 次执行通过，手机另验证整周 3→折叠 3→直接展开 3。这个回答包含具体触发、根因、代码改变和独立验证，不应只说“优化了日历”。依据：D05。

### 14. 完成、归档、删除的区别是什么？为什么恢复归档后可能仍在已完成列表？

完成记录 `completedAt`，归档记录 `archivedAt`，它们独立。归档时不会抹掉完成标记；恢复归档后仍有 `completedAt` 的事项自然回到已完成列表。删除才移除事项及其业务关联，界面要求明确确认。

完成和归档都会使截止前计划失效，恢复后再按当前时间、设置和已有账本判断是否安排。不能承诺恢复未完成会重复弹出已经送达过的同一业务提醒。依据：D06，Repository 的两套 setter 和 `ReminderPlanStore` 保留 SENT 的逻辑。

### 15. 为什么删除或完成事项以后，数据库里还有 reminder_plans 行？

提醒表兼作历史账本。事项状态失效后，将计划置为 inactive，并记录是否还有待撤销的系统通知；保留键和发送历史可帮助取消、重试与去重。`active=false` 与 `state=PENDING` 可以同时存在，不能只看 PENDING 字样判断仍会发送。

本轮 B 完成后只有 1 条 DEADLINE 计划，inactive、cancelPending=0，历史 state 仍为 PENDING；最后原 33 行加本批 5 行共 38 行，5 条测试事项已删除。这是数据生命周期设计，不是“QA 没清干净”。依据：D06 与[最终审计](../test-evidence/RUN-20261101-CALENDAR-FINAL/device/cleanup/final-data-and-state-audit.json)。

### 16. 图片为什么不能只存相册 URI？为什么粘贴网址不能当图片？

URI 的访问许可可能失效，外部来源内容也可能变化。项目把可读取的图片复制到应用私有目录并验证可解码，数据库记录自有文件名与元数据。普通网址文字没有当前可读取的图片内容，代码不把它自动下载成附件。

OBS-01 提示的是某些旧来源授权失效；明确提示和重新复制／从相册选择能帮助恢复，但不代表已修复所有提供方授权机制。依据：D03，`AttachmentStore.importImages/importOne`。

### 17. 删除附件会不会删掉相册原图？如何避免删错文件？

只处理应用私有附件目录中的自有副本；引用名须符合 UUID 格式，规范路径须仍位于该目录并拒绝符号链接越界。清理还会对照数据库仍在使用的文件，不删除外部原图。

删除草稿中的缩略图是草稿变化，保存后才决定旧副本是否不再被引用；取消编辑应保留原附件。多图导入失败会回滚本次已创建候选。依据：D03 的 `checkedFile`、`discardUnreferenced`、`rollback` 与 ViewModel 草稿管理。

### 18. 角色是不是 AI？为什么过滤了任务，表情没有按筛选变化？

是本地规则反馈和预设文本，没有在线聊天模型。函数先从全局有效事项选焦点，多个事项之间按危险、逾期、临近、正常优先；同状态按最早截止挑选。台词由十分钟时间段和焦点 ID 稳定选择，不会每次重组都随机变化。

首页传入全局 `state.events`，所以表情不跟随搜索结果缩小。完成成功时还有约 5 秒的 `justCompleted` 反馈；仅有历史完成记录不会长期触发欢呼。依据：D07。

### 19. 设置里切到 Q 版就已经保存了吗？换形象会改提醒吗？

设置页先改本地草稿并预览，点击“保存设置”才通过 ViewModel／Repository 保存 `characterStyle`。两种样式使用相同的业务状态和提醒规则，只改变素材显示。默认和未知值回退为 CLASSIC；schema 3→4 的迁移增加这个设置列并保留旧数据。

依据：D07 的 `SettingsScreen`、`CharacterStyle.fromStored`、`SaverDatabase.MIGRATION_3_4`。角色素材来源另有许可说明，应按真实来源回答。

### 20. 批量操作怎么避免只改成功一半？清除筛选会取消勾选吗？

点击操作后复制选中 ID 集合，Repository 在事务中先检查全部事项仍存在，再执行变化；失败则回滚。切换或清除筛选本身不会清空选择，所以不能仅根据当前可见行数判断待操作数量。

批量操作**成功后**有另一条链：ViewModel 返回 batch 动作 → `SaverApp` 更新 `batchToken` → `HomeScreen` 的 `LaunchedEffect(batchToken)` 自动退出批量并清空选择。它与“改变筛选不清选择”是不同触发。依据：D09；`SaverApp.kt` L148—150 与 `HomeScreen.kt` L48—50。

## 三、提醒环节的追问

### 21. “普通临近”、速通危险和提醒提前量是一回事吗？

不是。界面普通临近状态由 `urgentMinutes` 决定；速通危险由当前事项的 `sprintMinutes` 决定，留空就没有该危险期；临近截止通知提前量由 `deadlineLeadMinutes` 决定。三种提醒原因是 DAILY、DANGER、DEADLINE。

例如截止 18:00、速通 120 分钟、通知提前 60 分钟，危险提醒计划在 16:00，临近截止提醒在 17:00；界面是否已显示普通临近还取决于 `urgentMinutes`。重要程度不改变这些时间。依据：D01、D08。

### 22. 有很多事项时，是不是给每一条都设置一个系统闹钟？

数据库可以有很多计划，但系统用同一个 Alarm 身份安排最早的下一次唤醒。到点后重查所有到期有效计划并处理，再安排下一次。这减少系统调度状态与业务事项之间的分散对应。

这个设计使用 AlarmManager，不是 WorkManager，也不是依赖首页倒计时在后台一直执行。依据：D08，`ReminderRules.nextWake`、`ReminderEngine.reconcile`、`AndroidReminderPlatform.alarmIntent`。

### 23. 权限关了还能保存事项吗？“精确提醒”和“通知权限”一样吗？

可以保存，业务数据和计划仍持久存在。是否能发通知要综合运行时权限、App 总开关与通道；是否能精确排 Alarm 是另一个能力。不能通知时暂停系统唤醒，恢复后再校对；没有精确能力时使用可能延迟的近似安排。

依据：D08，`AndroidReminderPlatform.capabilities` 与 `scheduleAlarm`。用户授予通知权限不意味着设备一定允许精确 Alarm，更不保证所有省电条件下准时到秒。

### 24. 旧的闹钟回调来了，事项已经完成／删除了，会不会还提醒？

回调只是“请重新检查”的信号，引擎根据当前数据库重建计划、检查 active／截止／设置后才发送；完成／归档／删除也会留下撤销计划。旧回调参数不直接代表最新业务状态。

同一事项、截止、触发时刻的不同原因可以合并为一条通知；不同事项仍独立。依据：D08，`ReminderEngine.reconcile` L33—44 和 `content` L139—154。

### 25. 如何防止重复提醒？能保证严格只发一次吗？

计划键使用提醒类型、事项 ID、截止时间；账本保留已处理状态。真正发送前持久化 CLAIMED，再读当前状态，发送后写 SENT；失败保留重试依据。重复回调先看当前账本，已经 SENT 的同一业务键不简单重发。

但系统通知调用和数据库提交之间有中断窗口，不能保证所有崩溃条件下严格 exactly-once。稳定 notification tag、只提示一次标志、串行校对和重试降低影响；源码专门有发送成功／提交中断的测试。依据：D08 和 `ReminderEngineTest.kt` L338。

### 26. 手机上重启后为什么不总能恢复？你们代码不是有 BOOT_COMPLETED 吗？

Manifest 和 Receiver 只是实现入口，不等于真实设备已保证送达或完成调度。已有荣耀 X50 记录中，重启后不打开 App 的窗口没有恢复 Alarm／通知；普通打开后补发／重排成功，OBS-02 仍开放。现有证据还不能确定具体故障根因，不能未经证据就归因于某个系统厂商。

演示前正常打开 App 检查提醒；若老师问改进方向，可说明需要继续沿广播接收、异步恢复执行、权限和系统调度链路采证。不要为了显得完整声称“已支持所有后台场景”。

## 四、测试、版本与项目取舍

### 27. 你们如何验证？224 是什么，为什么还要真机？

最终本机构建解析出 29 份 JUnit XML，185 个不同方法、224 次实际执行，失败／错误／跳过各 0；部分方法在不同配置下执行，所以两种计数不能混用。纯规则、Room 事务／迁移和 Compose 页面回归各自验证不同层。

真机检查补充真实安装签名、原数据保持、系统 UI、图片来源和 OEM 通知条件。本次 0.3.5 真机完成日历矩阵及 18 项最终审计，不把所有更早的通知／图片观察算成本次重新执行。本轮没有新的远程 CI 通过结论；PR #14 的 CI 也不能移作手机 0.3.5 的测试结果。依据：[证据总入口](../test-evidence/RUN-20261101-CALENDAR-FINAL/README.md)。

### 28. 升级会不会丢数据？为什么演示不用远程最新 PR 的包？

数据库有显式迁移和历史 schema，手机同签名覆盖安装后还核对了原业务表、附件字节、设置、提醒记录及最终包身份。测试说明本次升级范围通过，不能推广成任意新迁移都一定安全。

演示、安装包、源码和证据应绑定同一版本。本材料固定 `demo-v0.3.5`；PR #14 尚在另一条开发线，涉及 schema 5 和重复任务，不属于这个已经验收的包。远程核对结果看[仓库快照](../acceptance-demo/00-version-and-repository-status.md)，不要用 PR 草稿界面讲解当前手机功能。

### 29. 这个版本能演示重复任务、云同步或 AI 聊天吗？

不能。0.3.5 有重复周期的纯计算基础，但没有用户可用的新建／管理重复任务界面；PR #14 才在独立开发存储和界面。应用也没有账号、云同步、应用内备份恢复或在线 AI 聊天。

可以把这些作为后续方向讨论，但必须说清“已有基础”“开发中的分支”和“当前手机已可用”是不同层次。角色的本地反馈已能演示，不能把它改称生成式对话。

### 30. 数据多了怎么办？目前实现还有什么取舍？

当前先观察本地完整事项列表，再在内存执行过滤、日期分组和排序，适合课程项目的小规模事项。当前已有关系表和附件索引；数据增大时可以考虑参数化 DAO 查询、按查询负载补充索引、分页、全文检索和增量统计。面向检索的新索引优化、分页、全文检索和增量统计尚未实现。

手写页面状态路由和直接构建依赖简单，但页面增多时可讨论类型化导航、依赖注入及模块拆分。说明取舍时先指当前实现，再提出可验证的改进，不把未来方案当成已有功能。

### 31. 离线保存是不是等于已加密、已备份？哪些工作是自己做的？

不是。数据保存在当前手机的数据库和私有文件目录，主 Manifest 禁用自动备份，当前没有应用内备份恢复；不能把这些事实说成已经实现端到端加密或云端容灾。卸载应用会影响应用私有数据，验收覆盖安装不能替换为卸载重装。

个人贡献按任务板、提交和真实参与回答；说明队友代码如何协作、自己能解释哪些部分，并如实区分 AI 辅助与个人实现。可以引用自己确实参与的功能理解、修复审查和实机验证，不虚构独立开发全过程。

## 五、老师追问后的备选深入讲解（约五分钟）

这不是功能演示结束后的固定环节，也不占前 5 分钟的展示时间。仅当老师要求整体走读且留出时间时，再采用以下路线；若只问一个功能，就只打开对应段。演示前可把它作为自学练习。

1. **40 秒：** 打开 `app/build.gradle.kts`，说清 Kotlin／Compose／Room 与 JDK／Gradle／Robolectric 的不同角色。
2. **70 秒：** 打开 `EventEditor` 保存入口、`RoomEventRepository.save` 与 `reminderTransaction`，沿一次保存解释草稿、校验、revision、事务和 Flow。
3. **60 秒：** 打开 `HomeScreen` L54—74，解释全局统计、日期列表和月格分布三种范围，再指出 L61 的折叠修复。
4. **50 秒：** 打开 `AttachmentStore.importOne` 或 `RoomEventRepository.setCompleted`，选自己演示的功能讲数据生命周期；不要两条链都讲得过于仓促。
5. **80 秒：** 若演示提醒，打开 `ReminderEngine.reconcile` 说“最新持久数据为准”，并说明权限／重启限制；否则打开角色函数说清全局状态和本地台词，再用最终测试记录说明证据范围。

练习结束时，检查自己能否不看答案说出：**一个入口函数、一次关键状态变化、一个持久化位置、一条测试证据、一个真实限制**。这些比背长依赖列表更能说明你理解了演示的软件。
