## 数据保持与提醒账本的区别

最终六张业务表为：`events` 7 条、`sources` 1 条、`tags` 1 条、`event_tags` 1 条、`custom_fields` 2 条、`attachments` 5 条。与[安装前摘要](before-data.json)相比，所有原业务行和五份附件的实际字节摘要保持一致；设置、字号、显示尺寸和密度恢复，schema 为 5，没有意外生成重复系列。最终包身份见 [final-identity.json](final-identity.json)，数据摘要见 [final-data.json](final-data.json)。

原始 [final-checks.json](final-checks.json) 中 `originalSentPreserved=false` **保留不改**。当时使用的是原 SENT 整行完全相同这一严格条件；真实时间已经跨过一条事项的截止时间，协调后该行的 `active` 从 1 变成 0，因此整行比较不相同。

随后只读对比原有 key 集合及每一列，[reminder-delta.json](reminder-delta.json)确认：

- 原 **17** 条 SENT 的 key 全部存在，状态仍为 SENT；除上述一行的 `active` 外，其余全部列保持。
- 那一行只发生 `active: 1→0`，且截止时间已过，符合提醒停用条件。
- 另 **1** 条原已存在的 DANGER 计划由 PENDING 记为 SENT，触发时刻在观察窗口内；最终 SENT 为 **18**。
- 提醒计划仍为 **46** 条，key 集合不增不减，没有删除或重写账本。

补充核对采用明确的调度边界后，[final-audit.json](final-audit.json)的 **21 项检查通过**，并记录原严格比较为何为 false。这里的 SENT 是 App 持久账本状态，**本轮没有据此宣称实际通知送达或点击已验证**。最终进程的 crash 缓冲未见 FATAL 记录；这也不是所有历史进程和长期运行条件的无崩溃证明。
